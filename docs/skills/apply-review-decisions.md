# Apply review decisions

Use when David says "the review is done", "done" after being sent the review sheet, or asks to apply decisions on a review-list Google Doc tied to a book project, such as his Ibn Ezra translation series.

Load **commentary-house-rules** first: it holds the standing rules for the book (translation, Hebrew letters, the (printed) [correction] form, transliteration, HASHEM); for this task also read docs/rules/review.md in the repo. The build itself is in **commentary-book-build**. This skill adds only how to apply decisions.

## Steps
0. **Which doc.** `git pull` the repo and look the doc up in `review_docs.json` (repo top): the open doc of the parasha David means, or the one he names. If more than one doc is open and he didn't say which, ask in one line. Set its status to `answered` once you have read his answers.
1. **Read the answers, not the doc.** In the Composio workbench, load scripts/workbench/wb.py (the load line is at its top) and run `read_answers('<parasha or doc id>')`. It reads the doc there with David's account (googledocs_spinet-dirk; never the default Going Pro account, never `proxy_execute`), keeps only ID / Decision chip / Your note for every row of the main tab (Decision and Your note columns found from each table's header row), checks the IDs against the rows file, commits `<rows file>` → `answers.json` to GitHub and prints a short summary with every note in full. Then `git pull` and work from answers.json plus the rows file (Where / Now / Alternative are there). Never load the whole doc into the conversation (a review doc is 2–3 MB). Run `scripts/check_review_doc.py` (check-review-doc) only when the doc's chips or links themselves need checking. The Drive text export leaves out chip answers, so never read decisions from it.
2. **Classify** each row: Approve / Keep / Change / Discuss / Unanswered. In the house meanings, Approve = do what the Proposal / Alternative column says and Keep = leave the book as it is (the Now column). A note with no chip still counts as an answer if it is clear (e.g. "Just get rid of 1:20, 2:4 & 1:1"). Unanswered rows are left completely untouched in the book. Discuss rows are not applied; list them back to David.
3. **Plan.** For each answered row, know exactly what changes in the source data (verse English, Hebrew display, comment lemma, note). When every answer is a plain Approve or Keep with no note, apply straight away and report. Show the plan first only when a note is ambiguous or two decisions conflict, and then ask.
4. **Follow-on wording.** When a row changes the verse English, also make the changes the row's Proposal or Explanation names: the comment's lemma (the italic heading quoting the verse), and any note that quotes the old wording or should now say "The verse translation follows this reading." Search the whole model (verses, ec, notes) for the old phrase. Places outside the row (e.g. Ibn Ezra quoting 3:5 inside his comment on 3:22) are not changed silently: report them and offer a new row.
5. **Names and rows with no ops** (9 Nov 2026): `review_audit/apply_answers.py` applies a names row itself (Approve changes the name in the parasha's work files; either answer goes into docs/rules/confirmed_names.json; a name also found in another parasha is reported for a book-wide row) and stops on any other approved row with no ops until it is made by hand and listed in `review_audit/<key>_by_hand.json`. A bundled row (one row for many places that only confirm the draft, `bundle` in the rows file; 9 Nov 2026) needs nothing on Approve or Keep — a bundled names row puts every name into confirmed_names.json — and on Change the script stops: make the places David numbered in Your note by hand. Reading the answers also brings the doc's progress line up to date.
5b. **Apply** in the project's source data, not the rendered output, one substitution at a time with an assert that the old text occurs exactly once: a parasha's work/chN.py files with `review_round/subs.py` (`sub(files, old, new, row_id)`; it escapes new quotation marks inside .py strings), then work/assemble.py; **Bereshit only through `bereshit/work/changes.py`** (entries `C(row, sec, (ch, v), old, new)`), then `python3 -I bereshit/work/build_model.py`; the front matter in bereshit/data/front.json. Write one apply script per review in review_round/ (e.g. apply_vowels1.py, apply_vayera1.py). For rows whose Now / Alternative are text windows, `scripts/rowdiff.py` (`raw_pair(raw, now, alt, others)`) turns them into an exact (old, new) pair of the raw markup, unique in the file set. Answers David gave in chat (`<rows file>` → chat_answers.json) override the chip. Never retype Hebrew from memory: substitute within the existing string. Back up the data first (a work folder such as /home/claude/workN), and log before/after for each row ID to review/draftN_applied_rows.json.
6. **Rebuild** with the project's pipeline (commentary-book-build), run `python3 -I scripts/check_all.py <folder>` (read every new hit; `--accept` once read), and look at the affected pages as images to confirm the change and that the layout didn't break. To find a page by its text, strip soft hyphens first (`pdftotext -f p -l p book.pdf - | sed 's/\xc2\xad//g'`), since the English is hyphenated.
7. **Final draft.** When this round makes the parasha final: remove "Draft for review" from the title page (data/front.json), name the PDF drafts/"<Commentator> <Parasha> - final.pdf", and set the parasha's status in book.json to final.
8. **Back up and deliver:** set the doc's status in review_docs.json to `applied` (note any unanswered or Discuss rows in its `note`), commit the data, the log, the PDF, book.json, review_docs.json and a README History line, push, then send the PDF with SendUserFile.
9. **Update the review doc** only where David asked (for example, marking applied rows), always through David's account. Never overwrite his Decision or Your note. Archiving the doc afterwards is in review-list-google-doc ("Archiving").
10. **Report** in a few lines: what was applied (by ID, with the new wording), what was skipped and why (unanswered rows by ID), anything found outside the rows, the page count and page numbers.

## Checks
- Diff the source data before and after: only rows with answered decisions (and their follow-on wording) may differ.
- Re-run the search for every misprint corrected, to make sure the (printed) [correction] form appears once and in the right place.
- Keep a backup of the source data before applying.
